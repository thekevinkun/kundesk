# Kundesk — Phase Handoff Document

> **Document Type:** Living document. Replace entirely after each phase completes. **Current State:** Phase 17 (Structured Business Knowledge) — Session 1 complete, backend only. Adds a form-based alternative to document upload: business owners can type in hours, contact, payment methods, menu/service items, FAQs, policies, and promos instead of writing a document, because many UMKM owners found document authoring too hard even with the Tip Panel. Eight PRs merged this session, in order: `feat/structured-knowledge-schema` (business_profiles/knowledge_sections/knowledge_entries tables; chunks gained nullable entry_id/section_id owner columns and a single-owner CHECK), `feat/knowledge-compile-helpers` (pure functions compiling form data into chunk text), `fix/kun-business-timezone` (KUN was reading the server's UTC clock with no zone label — production said "13.21 WITA" at 21.21 WITA; fixed with a proper `orgs.timezone` column and a rewritten `getCurrentDateTime`), `feat/knowledge-sync-layer` (`embedTexts` batching + `lib/knowledge/sync.ts`, embedding outside the DB transaction with a fingerprint check for concurrent saves), `feat/knowledge-actions` (the Server Actions — CRUD for sections/entries/profile, with CodeRabbit catching a stale-status bug and a summary-chunk orphan risk before merge), `feat/knowledge-profile-prompt` (business profile injected into `buildSystemPrompt`), `fix/kun-open-status-and-greeting` (KUN was asked to compare clock times and pick a greeting itself and got both wrong on a live account — "Malam" at 12.09 WITA, "tutup" while actually open; both are now computed in code via new `helpers/opening-hours.ts`, with a second CodeRabbit round fixing an equal-time/24:00 edge case, continuous-24h-coverage wording, and crash risks on legacy/malformed stored hours), and `refactor/knowledge-route` (moved the Documents page to `/dashboard/knowledge` with a `next.config.ts` redirect, after a redirect-page approach flashed an error screen). **No dashboard UI exists yet for any of this** — the whole backend was built and shipped behind Server Actions nothing calls yet, verified via direct Neon inserts and live chat testing on real accounts (Kedai Bu Sari and Rumah Paco sample documents used as the design's real-world test cases throughout). ### New Rules — Phase 16, Session 3

135. **Customer widget Pusher channel uses `private-conversation-{channelToken}` with a dedicated `/api/pusher/conversation-auth` endpoint** requiring a matching `sessionId` as a second factor against the `conversations` row. A leaked `channelToken` alone is no longer sufficient to subscribe — closes the last standing security item from the original audit. `sessionId` is sent via pusher-js's `paramsProvider`, reusing the exact `transport: "ajax"` config already proven for the dashboard's private channel (rule 113) — never invent a different transport.
136. **E2E coverage for channel auth lives in `e2e/06-pusher-channel-auth.spec.ts`** — unauthenticated suite (matches `01-public-chat.spec.ts`'s `storageState` pattern), covers wrong-sessionId (403), correct pair (200), and wrong-channel-prefix (403) cases. This suite doesn't depend on `auth.setup.ts` and can be run standalone with `--no-deps` when the setup project is flaky.
137. **Org deletion is a 30-day grace period, not instant.** `deleteOrg()` no longer calls Clerk directly — it stamps `orgs.deletionRequestedAt` and the org keeps full access. `cancelOrgDeletion()` reverses it. Historically, two daily crons existed here: `suspended-warning` (found orgs suspended 90+ days, sent one warning email, then started the same 30-day clock) and `org-purge` (found orgs whose grace period had fully expired and actually deleted them). **As of Session 4, `suspended-warning`'s trigger condition can no longer occur — see rule 144.** `org-purge` itself is unaffected and remains the only mechanism that actually deletes org data, now reachable exclusively via explicit owner-initiated deletion.
138. **`orgs.purgingAt` is an atomic claim marker** — the `org-purge` cron must claim an org via a conditional `UPDATE ... WHERE deletionRequestedAt IS NOT NULL AND purgingAt IS NULL RETURNING id` before acting on it, never act on a stale snapshot from an earlier `SELECT`. `cancelOrgDeletion()` and `activateSubscription()` must both check `purgingAt IS NULL` in their own `WHERE` clause before mutating — an org already claimed for purging can never be reactivated or have its deletion cancelled out from under the purge. This pattern closed three separate CodeRabbit-flagged races in one PR (cancel-during-purge, reactivate-during-purge-via-webhook, warning-before-clock-actually-starts). This is the canonical atomic-claim pattern for any future cron that permanently deletes or transitions something a user-facing action might race against — reuse it rather than inventing a new one. **Session 4 reused this same principle (check-return-value-before-reporting-success) for `downgradeToFree()` — see rule 145.**
139. **`org-purge` deletes the Clerk organization before the DB row, and treats an already-missing Clerk org (404) as success** — makes the cron safely retryable if a prior run got partway through. DB deletion runs in its own transaction; `payments.orgId` is anonymized automatically via `ON DELETE SET NULL` (rule 140) — no manual `UPDATE payments SET orgId = null` needed or wanted.
140. **`payments.orgId` is nullable with `onDelete: "set null"`**, not `cascade` — payment rows must survive org deletion for accounting retention (aggregate totals only; an anonymized payment is intentionally not queryable by org once purged — this was a deliberate decision, not an oversight, since anonymization only means something if the linkage is actually severed).

Fixed in the same PR as the `purgingAt` guard. The Midtrans webhook now wraps its transaction call in `try/catch`: if activation throws because the org is mid-purge, the webhook marks itself processed (stops Midtrans retries) and logs to Sentry for manual review, rather than surfacing an unhandled 500. Any function called from inside a `db.transaction()` block must actually accept and use the `tx` handle — check this specifically whenever wrapping an existing standalone query function in a new transaction.
142. **A live-database FK constraint's actual name can silently drift from what Drizzle assumes** — confirmed again in Session 3 (`payments_org_id_fkey` in Neon vs. Drizzle's expected `payments_org_id_orgs_id_fk`). Before writing any `DROP CONSTRAINT` in a manual migration, verify the real name first: `SELECT conname FROM pg_constraint WHERE conrelid = '{table}'::regclass AND contype = 'f';`. Never assume Drizzle's naming convention matches what's actually live. FK naming drift is an ongoing pattern, not a one-time fix — expect to re-verify actual constraint names in Neon before any future manual migration touching an older table.

153. **Midtrans reads the webhook's HTTP status as an instruction.** 2xx = stop retrying; a 500 is retried only once; a 503 is retried up to 4 times; Midtrans also expects a reply within about 5 seconds (per Midtrans's notification best-practices doc as read in Session 6). `POST /api/webhooks/midtrans` therefore keeps only body parsing in `POST` and wraps the rest (`processNotification`) in a try/catch that returns **503 + `Sentry.captureException`** for any unexpected error (Neon cold-start timeout, dropped connection). Never answer 200 for a payment that wasn't actually recorded. Not measured, worth watching: Neon cold start (2–5s, rule 112) plus the transaction against Midtrans's ~5s expectation and Vercel free tier's 10s function limit (rule 56) — idempotency makes a slow-then-retried notification safe, but it is a real latency budget.
154. **`processedWebhooks` is written only when an order's processing is actually finished** — successful activation (inside the transaction), fraud flag, amount mismatch, and the purge race. **Never** for `deny`, `expire`, `cancel` or `pending`. Reason: Snap lets a customer retry the same `order_id` after a failed attempt (card declined, then another method works); marking the failure "processed" made the later settlement look like a duplicate, so a paid customer was never upgraded. Current behavior: `deny` = log only, row stays `pending`, order still open; `expire` → `markPaymentClosed(..., "expired")`; `cancel` → `markPaymentClosed(..., "failed")` (no `.catch` — if the DB is down we want the 503 so Midtrans retries). Returning 200 already stops retries for these events; the extra "processed" mark was never needed.

Kevin ran the overdue-orgs query before production: empty. Confirmed while reading the cron: it DOES call `insertPendingPayment` right after creating the Snap transaction (rule 120 is followed), so the webhook's amount check covers renewals — the stale comments saying otherwise (webhook amount-check comment, `getPaymentByOrderId`) were corrected. The cron no longer logs the payment link (it contains the Snap token) — it logs the order ID.
166. **`markPastDue` restarts the grace clock: `nextBillingDate = GREATEST(nextBillingDate, NOW())`.** The past-due cron counts its 3-day warning and 7-day downgrade from `nextBillingDate`. Once rule 165 lets the renewal cron pick up a late org (say 10 days overdue), it charged the org at 08:00 WIB and the past-due cron downgraded it at 09:00 — one hour to use the new payment link. `GREATEST` leaves a normal due date untouched and restarts the clock at "now" for a late pickup. Side effect: the billing page shows the pickup date instead of the original due date for such orgs. This was found by reading the past-due cron AFTER the renewal PR had merged (no org was affected — the overdue query was empty) and fixed in the next PR.
167. **Past-due day-3 warning is now reliable.** The `>= 3` branch awaits `sendPastDueEmail` FIRST and records the `PASTDUE-{orgId}-{billingDate}` key AFTER the send succeeds, with `.onConflictDoNothing()` — a lost warning is worse than a duplicate one, and an un-awaited send on Vercel can be cut off after the key was already recorded (which meant no retry and a day-7 downgrade with no warning). If the send throws, nothing is recorded and tomorrow's run retries until the day-7 downgrade. An org with no `ownerEmail` is reported as `skipped` with a warning; failed orgs are now added to `results` as `failed` (they were silently dropped). **This depends on `sendEmail` in `lib/email.ts` throwing on any Resend error or timeout (verified in Session 6) — if that wrapper is ever changed to return an error object instead, this pattern and the renewal cron's `.catch` silently stop working.**
168. **`PastDueEmail` states the real consequence.** It previously said KUN "saat ini dibatasi" (is currently restricted) — true only in the pre-Session-4 "suspended" design. Since Session 4 a `past_due` org keeps full access until the day-7 downgrade to Free. The email now says the account is still fully active and that the plan drops to Free around `downgradeDate`. Signature: `sendPastDueEmail(to, orgName, amount, downgradeDate, logoUrl)`; the cron passes `nextBillingDate + 7 days`, formatted with `timeZone: "Asia/Jakarta"`. The button goes to `/dashboard/billing` (not to an old payment link), so an owner whose 24h Snap link has died starts a fresh payment from there. The renewal reminder email (`sendBillingReminderEmail`) still links straight to the Snap page, which dies after 24 hours — left as is, the day-3 email is the safety net.
169. **`expireStalePayments()` daily sweep** (`lib/db/queries/billing.ts`, called from `api/cron/retention` inside its own try/catch so a failure never blocks message retention; the retention response now includes `expiredPayments`). It marks every `pending` payment older than 24h as `expired`. Why: Snap sends no webhook when a checkout page merely expires (rule 157), and the other cleanup paths only cover owners who start a new payment (`insertPendingPayment` stale-row update), open the billing banner (`getPendingPayment` hides >24h rows) or picked a method that later expired (webhook). An owner who opens checkout, picks nothing and never returns kept a "PENDING" history row forever — four such rows from June–July 2026 were found in Neon; the first run of the sweep closes them. Safe because the Snap transaction is created with a 24h expiry, so Midtrans has already expired anything older.
170. **Email delivery blocker for the first real customer.** `lib/email.ts` sends from `Kundesk <onboarding@resend.dev>` and overrides the recipient with `RESEND_TO_EMAIL` when set (Resend's free sender only reaches a verified address). Until the domain is verified, `DEFAULT_FROM` is changed to the real domain, and the `RESEND_TO_EMAIL` override is removed, **no real owner receives any email** — renewal links, the past-due warning, upgrade receipts, handoff alerts. Already on the deferred list; treat it as a hard prerequisite together with Midtrans production activation.

## New Rules — Phase 17, Session 1

171. **Structured knowledge data model:** `business_profiles` (one row per org, PK = `org_id`) holds always-needed facts — `about`, `address`, `contacts` (JSONB `ContactItem[]`), `hours` (JSONB `HoursSchedule[]`), `paymentMethods` (JSONB `PaymentMethod[]`). `knowledge_sections` (`kind`: `catalog | faq | policy | promo | note`, `title`, `note`, `sortOrder`) groups `knowledge_entries` (`title`, `body`, `price` nullable JSONB `EntryPrice`, `isAvailable`, `sortOrder`, `syncStatus`: `synced | stale`). One entries table covers every kind — a FAQ's question/answer live in `title`/`body`, same as a policy's title/text. Chose this over one table per section kind specifically because Bu Sari (food) and Rumah Paco (vet clinic) needed the same shape under different labels.
172. **`chunks.document_id` is now nullable**; new nullable `entry_id` and `section_id` columns, each `ON DELETE CASCADE`. CHECK `chunks_single_owner_chk`: `num_nonnulls(document_id, entry_id, section_id) = 1` — every chunk has exactly one owner. Purely additive (dropped a NOT NULL, added nullable columns), so unlike rule 149's `midtransCustomerId` sequencing incident, this one could be applied to Neon before the matching PR merged with no risk to other in-flight branches.
173. **`EntryPrice` is a discriminated union**: `fixed` (single amount), `range` (min/max, e.g. Bu Sari's ikan bakar by size), `variants` (labeled options, e.g. Rumah Paco's sterilisasi priced by weight tier), `contact` ("hubungi kami"). Empty `variants` options list falls back to `contact` wording — KUN must never invent a price.
174. **A knowledge entry compiles to its own self-contained chunk** (`compileEntryChunks` in `helpers/knowledge.ts`), with a header repeated on every piece if the body is long enough to split (reuses `chunkText`, which does not add headers itself). A **catalog** section also gets summary chunks (`compileSectionSummaryChunks`) listing all its items compactly, because `retrieveContext`'s `MAX_CHUNKS = 5` can't surface every item individually for "apa saja menu sarapan?"-style questions. Summary chunks split at 800 chars with "(lanjutan N)" on continuation parts. A section under 2 entries gets no summary (would just duplicate the one item's own chunk).
175. **`isAvailable = false` means different things by section kind.** On a **catalog** entry it stays searchable with "Status: sedang tidak tersedia" appended to its chunk, so KUN says "lagi habis, Kak" instead of "tidak ada" — chunks are re-embedded, never deleted, on a habis toggle. On any **other** kind (FAQ/policy/promo/note) it compiles to zero chunks — this is how an owner switches off an ended promo.
176. **Always-needed profile facts (hours, address, contact, payment) go into the system prompt directly, not through retrieval** — decided over retrieving them as chunks specifically so they never compete for `MAX_CHUNKS = 5` retrieval slots on every message. `buildSystemPrompt`'s signature is now `(config, contextChunks, options: SystemPromptOptions)` where `options` is `{ timeZone?, profileBlock?, hours?, now? }` — one object, not loose positional params, so future callers can't mix them up. With no profile filled in, every org gets byte-identical prompt wording to before this feature — verified by a dedicated test.
177. **Neither the greeting nor the open/closed comparison is left to the model.** A real production account (Rumah Paco) got both wrong on `gpt-4o-mini`: it said "Malam, Kak!" at 12.09 WITA and said the clinic was closed while it was actually open, despite the correct time and correct hours being right there in its prompt — confirmed reproducible in a fresh incognito session with no chat history involved. New `helpers/opening-hours.ts` (pure, fully unit tested) computes both in code and the prompt states the result as fact with an explicit "jangan menghitung sendiri" instruction. `getGreetingPeriod`: Pagi 05–10, Siang 11–14, Sore 15–17, Malam 18–04 — this greeting fix applies to every org, not just ones with a profile.
178. **`HoursLine` is structured, not free text**: `{ days: number[] (0=Minggu..6=Sabtu), opens: "HH:MM", closes: "HH:MM" (may be "24:00"), note? }`. The original free-text form ("Senin – Jumat: 08.00–20.00") could not be computed against a clock. Zod (`hoursLineSchema`) rejects bad clock format, `opens === "24:00"`, `opens === closes`, empty or duplicate days.
179. **One shared line validator (`parseLine` in `opening-hours.ts`) guards every opening-hours code path** (`findOpenLine`, `findNextOpening`, `hasUsableLines`) — a CodeRabbit finding caught that an `08:00–08:00` line or an `opens: "24:00"` line could otherwise read as open. A schedule covering all 7 days as `00:00–24:00` reports "buka 24 jam setiap hari"; a full-day line whose next day also starts at `00:00` reports "lanjut buka melewati tengah malam"; otherwise a `24:00` close reports "tutup tengah malam" — a second CodeRabbit finding caught the first version reporting "tutup tengah malam" even for genuinely continuous 24-hour coverage.
180. **Stored hours are validated at every read boundary, not just at save time** (`parseStoredHours` in `helpers/knowledge-schemas.ts`, reused by both `lib/db/queries/knowledge.ts` and `lib/redis/index.ts`'s `getCachedProfile`) — a CodeRabbit finding: legacy-format or hand-edited-in-Neon hours (exactly what happened during manual testing of this feature) could otherwise reach `formatClock` with `undefined` fields and throw, taking down the whole profile block including address/contact/payment. A bad schedule is dropped **whole** (never half-read — a half-read schedule could tell customers wrong hours) and logged; the rest of the profile survives. A malformed cached entry counts as a cache miss, not a hit.
181. **The sync layer's write contract**: every Server Action that changes entry/section content must set `syncStatus: "stale"` and `updatedAt: now` in the **same** UPDATE statement, then call `syncEntry`/`syncSection`/`syncSectionSummary` from `lib/knowledge/sync.ts`. Embedding always happens **outside** any DB transaction (a slow OpenAI call must never hold a lock); the transaction that swaps old chunks for new ones re-locks the section + entry rows and compares an `updatedAt`-based fingerprint (`buildSectionSnapshot`) against what was read before embedding — if something changed mid-embed, the sync returns `superseded` and backs off, letting the newer save's own sync finish the job. If embedding itself fails (OpenAI down), old chunks are left untouched and searchable and the entry stays `stale` for retry — an owner never loses typed data to an API hiccup.
182. **Deleting the last (or second-to-last) entry of a catalog section deletes that section's summary chunks in the same transaction** — a CodeRabbit finding: since a section under 2 entries gets no summary chunk (rule 174), a stale summary from an earlier sync could otherwise survive with no stale-entry row left for `retryStaleKnowledgeSync` to ever find it through. Chose deleting the orphan risk over CodeRabbit's suggested alternative (a new durable section-level pending-sync marker column) — no schema change needed.
183. **`updateSection`'s "nothing changed, skip the sync" fast path must not report `synced` from field equality alone** — a CodeRabbit finding: a prior failed sync can leave a section's entries `stale`; if the owner re-submits identical values, the naive check reported `synced` without looking, hiding a needed retry. Fixed to check for existing stale entries first and run the sync as an implicit retry if any are found.
184. **`PLAN_LIMITS.knowledgeEntries`: Free 50, Starter 300, Pro 1000**, plus a flat `MAX_KNOWLEDGE_SECTIONS = 30` per org regardless of plan. Sized against the real sample documents — Kedai Bu Sari needs ~55 entries, Rumah Paco ~190. New `checkKnowledgeWriteLimit`: 200 saves/hour/org (every save calls OpenAI to embed; the existing 10/hour upload limiter was too strict for typing in a whole menu in one sitting). Create actions lock the org row before counting, then insert, inside one transaction — same pattern as the document upload route's plan-limit lock.
185. **`orgs.timezone`** (new column, default `Asia/Jakarta`) drives KUN's stated clock and the opening-hours computation — set per org manually in Neon for now, same as promo codes, until a settings screen exists. `getCurrentDateTime(timeZone?, now?)` was rewritten to actually convert via `Intl.DateTimeFormat` in the target zone and always print a zone label (named WIB/WITA/WIT for Indonesian zones, else "UTC±X" including half-hour offsets) — the original just read the server's local (UTC, on Vercel) clock with no conversion and no label, which is why production said "13.21 WITA" at 21.21 WITA. Falls back to `Asia/Jakarta` on an invalid zone instead of throwing.
186. **`/dashboard/documents` moved to `/dashboard/knowledge`**, in preparation for the page becoming a tabbed Profil/Dokumen (later +Katalog & FAQ) view rather than documents-only. Redirect is a `next.config.ts` `redirects()` entry (HTTP 308), **not** a redirect page inside the dashboard layout — a redirect page there flashed a "this page couldn't load" error screen for a moment in dev before firing, because the dashboard layout (Clerk auth, accent-color fetch) has to render first. The `next.config.ts` redirect answers before any layout or page runs. `DocumentsPage.tsx`, the `components/dashboard/documents/` folder, and `DocCountBadge` (still ready-documents-only) are deliberately unrenamed — they're still exactly what they say, and become the Dokumen tab's content once tabs exist.

### Root Cause, Named Explicitly (Recurring Themes Across All Six Sessions)

1. **Manual Neon application without keeping `schema.ts`/migrations in sync** — the discipline holds when deliberately applied (proven again in Session 3 for `purgingAt`, and in Session 5 for `midtransCustomerId`), but requires deliberate effort every time. Session 5 additionally surfaced that *merge order*, not just schema/code sync, matters: a manual Neon change applied before its matching code lands in `master` (via a real PR/CI gate, not a local-only merge) can break other in-flight branches that haven't caught up yet.
2. **The codebase's error-handling discipline (catch-and-log, never 500) means Sentry sees almost nothing** — still deferred as a full audit, Kevin's own call. Session 5 closed one specific instance of this (the document-processing pipeline's outer catch now explicitly reports to Sentry), but this was a side effect of a different fix (the `DocumentUserError` pattern), not the start of the deferred broader audit.
3. **Decisions made in one PR can silently create obligations in files not touched by that PR** (named in Session 2, reconfirmed in Session 3's reactivation-during-purge race, reconfirmed again in Session 4's downgrade fix silently invalidating Session 3's abandonment-purge trigger, and reconfirmed once more in Session 5: `orgs.suspendedAt` was flagged as a candidate for the same cleanup as `midtransCustomerId` purely because both looked structurally similar — "unused-looking column" — but a grep before acting revealed `suspendedAt` is still referenced by code, just by code whose trigger condition happens to be permanently false. Structural similarity between two cleanup candidates is not the same as actual equivalence — grep before generalizing a fix from one item to a look-alike).
4. **CodeRabbit's suggested diff is a starting point, not a drop-in fix** — Session 2's permission gates, Session 3's transaction-handle fix, Session 4's downgrade-race check, and Session 5's three document-upload findings (error leakage, abort propagation, orphaned-row cleanup) all required understanding surrounding code CodeRabbit's suggestion didn't fully account for on its own — in Session 5's case, correctly scoping the `DocumentUserError` distinction (which specific throws are safe to show verbatim vs. which wrap infrastructure errors) and correctly scoping the orphaned-row fix (delete on S3 PUT failure only, never on a later `/api/documents/process` failure, which already has its own correct `markFailed()` path).
5. **A status field left unenforced everywhere except one place (billing page display) is effectively decorative** — `subscriptionStatus` existed and was displayed correctly for months while `plan` was the only thing actually enforced anywhere. Worth checking, for any future status/flag field, whether every place that should read it actually does.
6. **Assumed third-party behavior, not verified live** — Session 6's first cancel design assumed Snap would refuse a page-cancel once a payment existed and that Core would then handle it; a real sandbox `/status` check showed the page died while the QRIS payment stayed `pending`. Reading the vendor's own retry rules (a response code is an instruction) also surfaced problems in a webhook that had already passed several reviews. Before trusting how a vendor behaves, run one real call against the sandbox and read the actual response.
7. **Failure paths were designed less carefully than happy paths** — the webhook had four solid defence layers on the happy path, but its failure paths (a blanket catch answering 200, failed attempts marked "processed", a swallowed DB error on the processed-marker insert) quietly undid them. When reviewing a handler, walk the error branches with the same care as the success branch and ask what the caller does with each status code.
8. **Changing which rows one cron selects can break the next cron in the chain** — the renewal fix (retry overdue orgs) would have made the past-due cron downgrade a late-picked-up org within an hour, because its grace clock counts from `nextBillingDate`. Found by reading the downstream cron after the first PR merged (no org was affected) — same lesson as theme 3, applied to the renewal → past-due → downgrade chain. Before changing a cron's selection, read every cron and email that acts on its output.

## Coding Rules Reminder (Session 5 & 6 Additions — Also See Rules 148–170 Above)

- **When a pipeline stage can leak infrastructure error text (S3, a third-party API, a raw DB error), never trust `err.message` to be client-safe by default.** Use a dedicated error class (e.g. `DocumentUserError`) to explicitly mark the specific throws that are genuinely meant to reach the user; everything else falls back to a generic message, with the real error still logged and reported to Sentry server-side. See rule 151.
- **An `AbortSignal` used for a pipeline timeout must be threaded through every async stage it's meant to bound — including fallback paths.** It's easy to wire a signal into the "happy path" of a pipeline and forget a fallback branch (like an OCR fallback) that was added later or handles a less-common case. Grep for every place a signal-bounded function calls another async function and confirm the signal is actually passed down, not just checked once at the top. See rule 151.
- **A resource created before a multi-step client-side flow completes (e.g. a DB row created before a direct-to-storage upload) needs an explicit cleanup path for every way that flow can fail, not just the "happy path" continuation.** The document-upload row was correctly marked `"failed"` when *processing* failed, but nothing cleaned it up when the earlier *upload* step failed — because the code that owns marking failure (`/api/documents/process`) is never reached in that case. When a flow has an early resource-creation step and a later ownership-of-failure step, check whether every earlier failure path is actually covered, not just the ones that reach the later step. See rule 151.
- **Grep before generalizing a cleanup from one item to a structurally similar one.** `orgs.suspendedAt` looked like the same kind of vestigial column as `orgs.midtransCustomerId` — same table, same "nothing sets a meaningful value here anymore" shape — but grep showed one is truly dead and the other is still read by live (if currently unreachable) code. Two things that look alike at a glance can have different actual states; check each one independently rather than batching them on the strength of the first one's answer. See rule 150.
- **A manual Neon schema change must land in `master` through the normal PR/CI gate — not a local-only `git merge` — before other in-flight branches can be trusted to still work.** A local merge to `master` skips exactly the check (CI, Playwright) that would have caught a branch left behind with a stale `schema.ts`. See rule 149.
- **`subscriptionStatus` must actually be read by every enforcement point that claims to gate on billing state.** The Session 4 bug existed because `subscriptionStatus` was displayed correctly on the billing page for months while zero enforcement code anywhere ever checked it — only `org.plan` was ever read. Before adding any new status/flag field, audit whether it needs to be checked in more than one place, and if so, verify it actually is everywhere it should be — don't assume a field being set means it's being used.
- **When a lapsed/failed state needs to eventually resolve, prefer an actual state transition (real downgrade) over a parallel "effective state" computed at each read site.** The rejected approach in Session 4 (`getEffectiveMessageLimit`/`getEffectivePlan` wrappers) would have required touching every enforcement location individually and left a permanent, correct-but-confusing "suspended but nominally still on old plan" limbo. A real, permanent state change (Session 4's `downgradeToFree`) made every existing check correct automatically with zero changes elsewhere — prefer this shape when it's available.
- **Never report success from a conditional write without checking it actually matched a row** — see rule 145. Same family as the `purgingAt` atomic-claim pattern (rule 138): a `WHERE`-guarded `UPDATE` can legitimately match zero rows under concurrency, and the caller must distinguish that from a real success.
- **A design decision made in one session can silently invalidate an assumption baked into a different session's earlier work, with no code overlap between them.** Session 4's billing fix retired the entire trigger condition Session 3's abandonment-purge cron depended on, without touching a single line of Session 3's actual files. When changing how a status/enum value gets set or transitions, grep for every place that value is checked or relied upon — not just the places that set it.
- **`purgingAt` is the canonical atomic-claim pattern for any future cron that permanently deletes or transitions something a user-facing action might race against.** See rule 138. Reuse this pattern rather than inventing a new one.
- **Any function called from inside a `db.transaction()` block must actually accept and use the `tx` handle** — see rule 141. Check this specifically whenever wrapping an existing standalone query function in a new transaction.
- **Verify live FK/constraint names directly before writing manual migration SQL** — see rule 142. Don't trust Drizzle's assumed name for any constraint that predates full Drizzle-managed migrations.
- **CodeRabbit's suggested code is a starting point — verify it against the actual surrounding code before applying.** See rule 25 and the root-cause notes above. Also worth noting from Session 4: not every CodeRabbit finding needs a code change — one finding was resolved by confirming an already-planned manual step covered it, which is a legitimate resolution as long as it's actually verified, not just asserted. Session 5 reconfirmed this from the opposite direction — all three of its CodeRabbit findings DID need real code changes, and each required tracing the surrounding pipeline/hook logic to scope the fix correctly rather than applying the suggested diff verbatim.

### Session 6 Additions

- **A webhook's status code is an instruction to the sender.** Return 200 only for a payment that is recorded or deliberately ignored; return 503 for anything transient so the sender retries. See rules 153–155.
- **Only mark an event "processed" when the order's work is truly finished.** A failed attempt that can be retried must never write to the idempotency table. See rule 154.
- **Use a named error class to separate the one expected failure from everything else, and rethrow the rest.** `OrgPurgingError` (rule 155) follows `DocumentUserError` (rule 151). A blanket `catch` that answers "handled" hides real outages.
- **Use `.onConflictDoNothing()` for a duplicate-tolerant insert, never `.catch(() => {})`.** See rule 156.
- **Closing something at a third party means closing everything that can still be used** — for a Snap order that is the payment AND the page. Report success only on an explicit confirmation from the vendor; an ambiguous or unreadable response is "not confirmed" and the local record must stay as it was. See rule 158.
- **Test a vendor's behavior with one real sandbox call before designing around an assumption** — and remember that a curl bypasses your own DB. See rule 164.
- **Test-mocking pitfalls seen in Session 6:** a shared `Response` object can only be read once; a class used with `instanceof` must live inside the `vi.mock` factory. See rule 163.
- **Before changing which rows one cron selects, read every downstream cron and email that acts on the result.** The renewal → past-due → downgrade chain shares one clock (`nextBillingDate`). See rules 165–166.
- **When a side effect (an email) must succeed before an idempotency key is recorded, await it and record the key afterwards.** A duplicate is better than a silently lost warning. See rule 167.
- **A state no vendor event will ever close needs a sweep.** Snap sends nothing when an unused checkout page expires, so a daily cleanup owns that transition. See rule 169.
- **After a behavior change, grep the owner-facing copy (emails, banners) for claims about the old behavior.** Session 4 made `past_due` fully active, but the warning email kept saying the account was restricted until Session 6. See rule 168.
