### New Rules — Phase 16, Session 3

135. **Customer widget Pusher channel uses `private-conversation-{channelToken}` with a dedicated `/api/pusher/conversation-auth` endpoint** requiring a matching `sessionId` as a second factor against the `conversations` row. A leaked `channelToken` alone is no longer sufficient to subscribe — closes the last standing security item from the original audit. `sessionId` is sent via pusher-js's `paramsProvider`, reusing the exact `transport: "ajax"` config already proven for the dashboard's private channel (rule 113) — never invent a different transport.
136. **E2E coverage for channel auth lives in `e2e/06-pusher-channel-auth.spec.ts`** — unauthenticated suite (matches `01-public-chat.spec.ts`'s `storageState` pattern), covers wrong-sessionId (403), correct pair (200), and wrong-channel-prefix (403) cases. This suite doesn't depend on `auth.setup.ts` and can be run standalone with `--no-deps` when the setup project is flaky.
137. **Org deletion is a 30-day grace period, not instant.** `deleteOrg()` no longer calls Clerk directly — it stamps `orgs.deletionRequestedAt` and the org keeps full access. `cancelOrgDeletion()` reverses it. Historically, two daily crons existed here: `suspended-warning` (found orgs suspended 90+ days, sent one warning email, then started the same 30-day clock) and `org-purge` (found orgs whose grace period had fully expired and actually deleted them). **As of Session 4, `suspended-warning`'s trigger condition can no longer occur — see rule 144.** `org-purge` itself is unaffected and remains the only mechanism that actually deletes org data, now reachable exclusively via explicit owner-initiated deletion.
138. **`orgs.purgingAt` is an atomic claim marker** — the `org-purge` cron must claim an org via a conditional `UPDATE ... WHERE deletionRequestedAt IS NOT NULL AND purgingAt IS NULL RETURNING id` before acting on it, never act on a stale snapshot from an earlier `SELECT`. `cancelOrgDeletion()` and `activateSubscription()` must both check `purgingAt IS NULL` in their own `WHERE` clause before mutating — an org already claimed for purging can never be reactivated or have its deletion cancelled out from under the purge. This is the canonical atomic-claim pattern for any future cron that permanently deletes or transitions something a user-facing action might race against — reuse it rather than inventing a new one.
139. **`org-purge` deletes the Clerk organization before the DB row, and treats an already-missing Clerk org (404) as success** — makes the cron safely retryable if a prior run got partway through. DB deletion runs in its own transaction; `payments.orgId` is anonymized automatically via `ON DELETE SET NULL` (rule 140) — no manual `UPDATE payments SET orgId = null` needed or wanted.
140. **`payments.orgId` is nullable with `onDelete: "set null"`**, not `cascade` — payment rows must survive org deletion for accounting retention (aggregate totals only; an anonymized payment is intentionally not queryable by org once purged).

### Rule 201 — the orphaned-summary-chunk investigation, told honestly

This deserves its own numbered entry rather than being folded into rule 199, because the investigation itself — including a wrong turn Claude made and then corrected without Kevin having to catch it — is worth remembering more than the final test code is.

**What was observed:** running the orphan-chunk test locally, after creating two real catalog entries (A then B) through the actual dashboard UI and confirming via direct DB query that *neither* entry was `syncStatus: "stale"`, the test's own sanity check — "the section should have at least one summary chunk by now, since it has 2 entries" — failed. `summaryBefore` was `0`.

**Claude's first theory**, formed from reading `lib/knowledge/sync.ts`'s `syncEntry` → `syncSectionChunks` path: that `syncEntry(orgId, B.id)` does an *unlocked* `db.select()` of the section's entries before embedding (to decide what to compile), and that this read could plausibly race B's own just-committed insert — reading `[B]` only, missing `A`, which would make `compileSectionSummaryChunks` correctly return `[]` (since it requires 2+ entries) even though 2 entries genuinely existed a moment later.

**Why that theory doesn't survive scrutiny of the actual code**, on a second, more careful pass: `syncSectionChunks` doesn't just read once and trust it. It captures a fingerprint (`buildSectionSnapshot`) of exactly what it read *before* embedding, then — inside the transaction, after embedding, with the section and entry rows now row-locked — re-reads and re-fingerprints, comparing the two. If the pre-embed read had genuinely missed entry A, the locked re-read (happening after A's insert has certainly committed, given the timing of a real UI click sequence) would very likely see both A and B, the fingerprints would disagree, and the function would return `"superseded"` — which leaves the entry `stale`, not `synced`. The observed outcome (both entries `synced`, no stale rows, yet no summary) doesn't fit through any branch of this code as written: for both entries to end up `synced`, the pre-embed read and the locked read must have agreed with each other on the entry set; and if they agreed and both saw 2 entries, a summary chunk should have been built.

**Where this was left:** Claude presented this reasoning to Kevin plainly — including that the first theory was wrong, not just less certain — rather than picking a second unverified guess to replace the first one, and rather than quietly loosening the test's assertion to make the failure go away. The actual root cause is **not confirmed**. It could be a real, rarer bug somewhere `sync.ts` wasn't traced carefully enough for; it could be a one-off Neon connection or timing anomaly unrelated to this code at all. No further static tracing was attempted after the disproof — the deliberate decision (Kevin's call) was to stop guessing from source and instead **reproduce it on purpose, manually, in the real dashboard, in Session 3**, treating this the same documented-but-not-chased way rule 143 already treats `auth.setup.ts`'s flakiness.

**What the test does in the meantime, so it isn't blocked on an open question:** the orphan-chunk test now forces a full section resync — via the dashboard's own "Edit bagian" → "Simpan" flow on the section's note field, which triggers `updateSection`'s real-change path (flags every entry `stale`, then calls `syncSection` with the full `"all"` scope, a fresh locked read rather than the narrower per-entry path) — and waits for that resync to fully clear before asserting the summary chunk exists. This measures the actual before/after guarantee the test is meant to cover, without the pass/fail outcome depending on whatever caused the one observed case.
