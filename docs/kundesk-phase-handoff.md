### Rule 201 — the orphaned-summary-chunk investigation, told honestly

**What was observed:** creating two real catalog entries (A then B) via the dashboard UI, confirming via DB query that neither was `stale`, the test's own sanity check — "the section should have at least one summary chunk by now" — failed. `summaryBefore` was `0`.

**Claude's first theory:** an unlocked pre-embed read in `syncEntry` racing entry B's own just-committed insert, missing A, correctly returning no summary for what looked like 1 entry.

**Why that theory doesn't survive scrutiny:** `syncSectionChunks` fingerprints its pre-embed read, then re-reads and re-fingerprints inside the transaction after embedding, with rows locked. A mismatch returns `"superseded"`, leaving the entry `stale` — not `synced`. The observed outcome (both entries `synced`, no stale rows, no summary) doesn't fit any branch of the code as written.

**Where this was left after Session 2:** the actual root cause was not confirmed. No further static tracing was attempted after the disproof — the deliberate decision (Kevin's call) was to stop guessing from source and instead **reproduce it on purpose, manually, in Session 4**, treating this the same documented-but-not-chased way rule 143 already treats `auth.setup.ts`'s flakiness.

**What Session 4 actually did about it — three separate manual repro attempts, all on a fresh test org ("Warung Paco"), all negative:**

1. **Sequential multi-entry add** — three catalog entries added one at a time, a few seconds to a couple of minutes apart, through the real dashboard UI, checking the DB after each save. Every entry correctly got its own chunk, and the section's summary chunk appeared correctly and promptly once entry count reached 2+. No orphan.
2. **Rapid repeated single-entry edit** — the same catalog entry (Es Teh Manis) edited three times in quick succession (including a double-back-and-forth price change) without waiting for save confirmations between edits. This also directly revealed that the sync mechanism is **delete-then-recreate, not update-in-place**: every save produced a brand-new chunk `id` for both the entry chunk and the section summary chunk, sharing an identical `created_at` timestamp each time. This is now understood as the real theoretical mechanism that *could* produce rule 201's symptom under the right interruption (a crash or timeout landing exactly in the gap between delete and recreate) — but even three rapid edits in a row, through the real dashboard, never actually hit that window. Final state was always correct: exactly one summary chunk, one entry chunk, entry `synced`.
3. **Genuine two-tab concurrent edit** — two separate browser tabs open at once, both editing the *same* entry, each saving a different price close together. This is the first attempt that actually produced a visible symptom: Tab A's save was correctly detected as superseded by the sync layer's fingerprint-and-relock check, surfacing the real per-entry equivalent of the `StaleSyncBanner` ("1 entri belum tersinkron dengan KUN" / "Menunggu sinkronisasi") in Tab A's UI, while Tab B's save completed as the authoritative one. Critically, **the database was never actually wrong at any point** — it was already fully correct and consistent (one entry chunk, one summary chunk, both reflecting Tab B's price) the moment Tab A's stale badge appeared. Clicking "Coba lagi" in Tab A cleared the badge with zero DB changes — no new chunk ids, no duplicate, no revert — confirming the retry correctly recognized an already-synced state as a true no-op.

**Where this leaves rule 201 at the close of Phase 17:** the root cause remains genuinely unconfirmed. But confidence in the sync layer's core safety mechanism is now meaningfully higher than it was after Session 2's purely static analysis — a real concurrent-tab race was deliberately created, and the system converted it into a visible, safely-recoverable `stale` state rather than a silent orphan, exactly as the fingerprint-and-relock design is supposed to do. The practical implication: if rule 201's original symptom (synced entries, zero summary chunk, no stale flag anywhere) ever recurs, it most likely needs either (a) genuinely degraded network/production-latency conditions that a fast local dev environment can't reproduce, (b) a different code path entirely — e.g. a deletion racing a sync, rather than two syncs racing each other — or (c) passive monitoring in production rather than further active local repro attempts, since three honest tries across three different mechanisms couldn't surface it.

**Why this is still worth flagging to the next phase explicitly:** if the original bug is real and rare, any business owner's catalog section could in principle go from 1 to 2 entries and end up fully `synced` while KUN still can't answer catalog-listing questions — with nothing surfacing that gap in production today, since the stale-sync banner only reacts to `stale` entries, which this symptom (by definition) does not produce. A lightweight production health check — e.g. a periodic query for catalog sections with 2+ synced entries and zero summary chunks — would catch this class of issue if it exists, without needing to reproduce it manually first. Not scoped or built; just the clearest concrete next step if this is picked back up.

253. **Checkout-row checks in `settlePaidOrder`.** (a) In real mode (`env.paymentMode !== "mock"`), no checkout row → refused, 200 + Sentry error `midtrans webhook: settled payment has no checkout record`; mock mode keeps the old fallback. (b) The row's `orgId` must start with the order_id's 8-char slice and its `plan` must equal the order_id's plan; a mismatch = Sentry error, marked processed (`.onConflictDoNothing()`), 200. (c) A settlement for a row whose status is not `pending` (cancelled/expired/failed) is **still activated** — real money arrived — with a Sentry warning `midtrans webhook: settlement for a non-pending order`. **This supersedes rule 160's "known gap":** it is now deliberately handled by logging, not blocking. (d) The amount check stays and now also marks processed with `.onConflictDoNothing()`. `gross_amount` is read with `parseInt`, so Midtrans's `"99000.00"` becomes 99000.

254. **Permanent failures answer 200 + Sentry — never 400, never silent.** Unparseable order_id, no checkout record, order/plan mismatch, org resolution failed, amount mismatch, fraud flag, post-purge activation failure: a retry cannot fix any of them, but the money is real, so each raises a Sentry message (`level: "error"`, one fixed string per case so alerts group). Only invalid JSON / invalid body shape stays 400. This extends rules 153–156: transient failures (DB timeout, dropped connection) still rethrow → 503 so Midtrans retries.

255. **A settlement/capture must carry `status_code "200"`; the check runs AFTER the fraud check on purpose.** `status_code` is covered by the signature but `transaction_status` is not, so this blocks a replayed signed "pending" notification with a flipped status. A challenged card capture legitimately arrives with `status_code "201"` and must reach the fraud branch, not be swallowed as "inconsistent". A mismatch = Sentry warning, 200, no action.

256. **Unique-violation handling inside the activation transaction.** If the transaction fails with a Postgres `23505`, the code re-selects `processedWebhooks`: marker present → `already_processed` (200); marker absent → rethrow (503), because the violation came from somewhere else. `isUniqueViolation` checks both `err.code` and `err.cause.code`. **That Drizzle may wrap driver errors in a `cause` was a precaution, not confirmed against this project's driver.** Both shapes are unit-tested. `OrgPurgingError` handling (rule 155) is unchanged.

257. **Post-commit work can never turn a recorded payment into a 503.** After the transaction commits: `createNotification` is awaited inside try/catch (a failure → `Sentry.captureException`, the response is still 200); the upgrade email and the PostHog `plan_upgraded` event run inside `after()` from `next/server` — Vercel keeps the function alive until they finish, while plain fire-and-forget could be cut off — each in its own try/catch; an org with no `ownerEmail` skips the email (previously `ownerEmail ?? ""` sent to an empty address). This replaces the old "email fire-and-forget, analytics awaited" pattern.

258. **Signature verification.** `verifyMidtransSignature` compares with `timingSafeEqual`, after a `typeof` guard and a length guard (`timingSafeEqual` throws on unequal lengths, so a wrong length must be a clean `false`). **The formula is plain SHA-512, NOT an HMAC** — the old comments claiming HMAC-SHA512 in `lib/midtrans/index.ts` (two places) were wrong; the code was always correct, and the comments were fixed.

259. **`getPaymentByOrderId` now returns `{ orgId: string | null, plan, amount, status } | null`** (it used to return only `{ amount, status }`). `orgId` is nullable because `payments.orgId` is `ON DELETE SET NULL` (rule 140).

260. **`getMidtransTransactionStatus(orderId)` in `lib/midtrans/index.ts` asks the Midtrans Core API `GET /v2/{order}/status`.** Result is `MidtransStatusResult`: `{ found: false }` or `{ found: true, statusCode, transactionStatus, fraudStatus?, grossAmount, paymentType }`. **The response shapes were verified live against the sandbox, not taken from docs (rule 164):** a paid QRIS order returned `status_code "200"`, `transaction_status "settlement"`, `fraud_status "accept"`, `gross_amount "99000.00"`; an expired order, a cancelled order and a made-up order id all returned `status_code "404"` / "Transaction doesn't exist." — and the 404 arrives **inside the body**. 261. **`/api/cron/payment-reconcile` is the eighth cron, `0 19 * * *` (19:00 UTC / 02:00 WIB), confirmed present in Vercel → Settings → Cron Jobs.** It uses the same `CRON_SECRET` Bearer auth. **Step 1, reconcile** (skipped in mock mode): up to `BATCH_SIZE = 10` candidates; Get Status calls in parallel (`Promise.allSettled`); settlements one at a time. ### Root Cause, Named Explicitly (Recurring Themes)

1. **Manual Neon application without keeping `schema.ts`/migrations in sync** — the discipline holds when deliberately applied, but requires deliberate effort every time. Merge order, not just schema/code sync, matters (Phase 16 Session 5).
2. **The codebase's error-handling discipline (catch-and-log, never 500) means Sentry sees almost nothing** — still deferred as a full audit, Kevin's own call.
3. **Decisions made in one PR can silently create obligations in files not touched by that PR** — named repeatedly since Phase 16 Session 2.
4. **CodeRabbit's suggested diff is a starting point, not a drop-in fix** — reconfirmed in Phase 17 Session 2's two CodeRabbit rounds, requiring tracing surrounding code to scope the fix correctly.
5. **A status field left unenforced everywhere except one place is effectively decorative** — `subscriptionStatus` existed and displayed correctly for months while `plan` was the only thing actually enforced anywhere.
6. **Assumed third-party behavior, not verified live** — Session 6's Midtrans cancel design assumed vendor behavior a real sandbox call disproved.
7. **Failure paths were designed less carefully than happy paths** — the Midtrans webhook had solid happy-path defenses but quietly-undoing failure paths.
8. **Changing which rows one cron selects can break the next cron in the chain** — the renewal → past-due → downgrade chain shares one clock.
9. **A disproven hypothesis is still worth writing down, in full, rather than replaced with a second unverified guess.** Phase 17 Session 2's orphan-chunk investigation (rule 201) is the clearest example: the honest move was presenting the dead end exactly as it happened, including which specific mechanism made the first theory impossible, rather than quietly swapping in a different guess to look more conclusive. **Phase 17 Session 4 extended this same discipline across three further repro attempts, all honestly reported as negative, with the one genuinely new finding (the delete-then-recreate sync mechanism, and the positive validation of the fingerprint-and-relock safety check) clearly separated from what remains unconfirmed.**
10. **A file already seen once in a long session can still go stale in memory by the time it's diffed against again** — Phase 17 Session 2's two file-diff mistakes trace back to this. Worth a habit of re-verifying rather than reconstructing from earlier in the same conversation once several turns and several other files have passed.
11. **A recommended decision that isn't visibly acted on needs an explicit statement either way, not silence.** Phase 17 Session 3's "Isi Manual" naming lapse: Claude proposed the name, got sign-off to decide, then genuinely forgot to apply it in the next rewrite with zero flag in either direction — indistinguishable, from Kevin's side, from having silently overridden his own earlier input. Silence about a prior recommendation is never a safe default, whether or not the omission was deliberate.
12. **When the person has already stated a direction and says it doesn't need to be followed exactly, further multiple-choice questions read as deflection, not diligence.** Phase 17 Session 3: three structural UI questions handed back via a picker tool after Kevin had already given a mockup and explicit latitude — the right move was to decide and show the reasoning, not to ask again in a different format.
13. **A prompt instruction written for one fact doesn't automatically cover an adjacent fact, even when both are injected the same way.** Phase 17 Session 4's datetime-refusal bug (rule 217): the open/closed status line had explicit permission to be stated back to a customer; the datetime line, injected identically, never got the equivalent sentence. Noticing the asymmetry between two side-by-side instructions — not just the symptom of one of them failing — was what found the actual fix.
14. **Multi-turn LLM context can override a correctly-recomputed system-prompt fact with the model's own prior, possibly-wrong turn still sitting in conversation history.** Phase 17 Session 4's status-bleed bug (rule 219) is a clean example: the ground truth was right in the prompt on every single turn, and the model still leaned on its own earlier answer. The fix (an explicit override instruction) is a mitigation on model behavior, not a deterministic code fix — this class of bug can recur in a different shape and should be watched for, not considered permanently closed.
15. **A delete-then-recreate sync pattern is a reasonable, defensible implementation choice, but it inherently opens a race window that update-in-place wouldn't have.** Phase 17 Session 4 confirmed this is genuinely how the knowledge-chunk sync works, and used it to explain rule 201's theoretical mechanism — but three separate manual attempts (sequential add, rapid single-entry edit, concurrent two-tab edit) couldn't actually force a failure through that window locally, strengthening confidence in the surrounding safety check without resolving the original mystery.
16. **Treating a diagnostic side-test as if it settles the user's original, still-open complaint is a real failure mode.** Phase 17 Session 4: a single incognito test correctly answered one narrow sub-question (history contamination vs. structural prompt gap) but did not touch any of the three bugs Kevin had actually reported — and was briefly treated as if it had. Caught directly by Kevin, not self-caught. Worth checking explicitly, after any diagnostic detour, whether the original reported problem is actually back in scope.
17. **Guessing a database table's schema from memory or naming convention, instead of querying `information_schema` first, wastes a turn and produces a confidently wrong result.** Phase 17 Session 4 hit this directly (rule 225) — the same underlying discipline as rule 1's "keep `schema.ts` in sync" lesson, just applied on the read side rather than the write side: never assume a column name or table shape mid-session, even when it feels obvious from a similar table seen earlier.
18. **When one surface follows a different data source than another, fix it at the source of truth, not at each caller.** The Topbar clock and the dashboard queries followed the browser while KUN followed the DB. Because every query already took a `timezone` param, changing what `getOwnerTimezone()` returns fixed three callers without touching any of them. Look for the single function every consumer already goes through before editing the consumers.

20. **`revalidatePath` refreshes server-rendered output, never the client's TanStack Query cache.** Anything a server action changes that a mounted `useQuery` also displays needs an explicit `invalidateQueries`. Missed twice this session (picker save, then auto-detect) — both caught by CodeRabbit.
